# Aura requirements

1. Implement Intent → Plan → Implement → Verify → Learn → Update → Continue.
2. Sol decomposes work into dependency-aware, bounded slices.
3. DeepSeek and Luna have separate worktrees, packets, contexts, and candidate identities.
4. Dispatch concurrent work only when dependencies and write conflicts permit it.
5. The deterministic Governor enforces authority, scope, budgets, transitions, and recovery.
6. Astra independently verifies exact candidates without builder reasoning.
7. Centrally validate the combined integration candidate; candidate mutation invalidates audit.
8. Detect repetition and lack of progress; allow at most two materially different repairs.
9. Escalate exhausted coding repairs to Sol; distinguish environment, access, and owner blocks.
10. Persist UNKNOWN effects and reconcile before retrying after interruptions.
11. Record attributable strategy, checks, outcomes, and lesson evidence.
12. Require authenticated independent review before a lesson becomes retrievable.
13. Share reviewed lessons across lanes while pinning each active slice's snapshot.
14. Compare only compatible contexts, checks, and metrics; quality precedes speed or cost.
15. Withdraw harmful lessons without rewriting historical evidence.
16. Persist knowledge and replay state without duplicating external effects.
17. Configure verified provider IDs for the owner-selected roles; no silent substitutions.
18. Resolve the Luna/Astra cross-family-policy conflict before activating that pairing.
19. Provision production review verification against owner-pinned trust.
20. Demonstrate one real task, two parallel tasks, forced stuck recovery, restart, and a
    reviewed lesson measurably changing a later strategy and outcome.
21. Keep paid execution, publication, deployment, and destructive authority explicit.
22. Treat offline proofs as mechanism tests, not evidence of live operational completion.
23. Deliver Aura as Nick's personal autonomous coding CLI with his selected agent structure.
24. Provide an interactive `aura` entry point and init, build, status, inspect, pause and resume commands; retain forge compatibility.
25. Show task progress, active agents, checks, costs where known, and actionable blockers in a clear terminal interface.
26. Include persistent memory, skills and restart support in the first usable release.
27. Store owner preferences, project decisions and searchable session/build history with provenance and time context.
28. Retrieve relevant memory by project and task; keep unrelated project context separate and current owner intent authoritative.
29. Allow memory inspection, correction, removal and export; keep credentials outside memory.
30. Load versioned SKILL.md procedures on demand, with provenance, dependency inspection and rollback.
31. Review agent-proposed reusable procedures before sharing them with future tasks; pin active task memory/skill snapshots.
32. Persist the objective, plan, assignments, candidate/worktree identity, checkpoints, budget and next action across sessions.
33. Reconcile repository, process and provider state after interruption; never automatically repeat an uncertain external effect.
34. Implement one application with a terminal, coordinator, execution engine, storage and verification; define storage authority explicitly.
35. Use SQLite for queryable runtime/session/memory data and Markdown for readable guidance; reuse validated ledgers without conflicting state authorities.
36. Accept a repository, objective, acceptance criteria, allowed scope and budget as a bounded autonomous work order.
37. Continue authorized work through planning, implementation, testing, independent review and repair without asking for routine reconfirmation.
38. Escalate consequential missing owner decisions or exhausted recovery with precise evidence and the minimum action needed.
39. Demonstrate a real single-builder coding path first, then session continuity and skills; both are required for the first usable release.
40. Demonstrate two concurrent independent builder tasks and fresh review of their combined integration candidate.
41. Demonstrate an unattended multi-task feature build with bounded spending, stuck recovery and safe restart.
42. Support later remote execution with terminal reconnection; an always-on host is required when the owner's PC is off.
43. Report final candidate identity, checks, review, changes, measured cost or UNKNOWN, and remaining blockers.
44. Measure accepted builds, regressions, completion time, cost, owner interventions and lesson effectiveness on representative tasks.
45. Consolidate useful draft work without a wholesale rewrite; preserve historical evidence and distinguish product targets from implemented status.
